# コード品質ルール（src全般）

## コメントの書き方

参考：https://zenn.dev/k_tabuchi/articles/60bddccd7dfcaa の方針に固定する。
外部向け（JSDoc）と内部向け（`//`）を分け、「なぜ」だけを書き、「何をしているか」は
コードに語らせる。

- **JSDoc（`/** */`）は仕様説明として、外部から参照されうる部分にだけ使う**：
  コンポーネント自体・exportされた関数・カスタムフック・utils等の共有関数。
  ファイル先頭にはファイル名の直後に、そのファイルの役割を1〜3行程度で書く。
  処理の流れを箇条書きで書き出さない（内容はコードを読めば分かる）
  ```
  /**
   * src/xxx/Yyy.tsx
   * （このファイルの役割。1〜3行）
   */
  ```
  引数・戻り値が自明でない共有関数には`@param` `@returns`を付ける
  ```
  /**
   * ログイン処理を行う。
   * @param userName - ユーザー名
   * @returns アクセストークン
   */
  ```
- **`//`コメントはコンポーネント内部ロジックに使う**：useEffectの意図、ローカル
  ハンドラー（handleXxx）、条件分岐の補足など。1〜2行程度で、非自明な「なぜ」
  だけを書く（例：iOS Safariのタッチ操作でネイティブD&Dが効かないため、等）
- **明らかにコードから読み取れることは書かない**：変数名・関数名・型で説明が
  付くものに重ねて説明コメントを書かない
- **過剰なコメントは可読性を下げるため避ける**：非自明な「なぜ」（複雑な計算
  ロジック、他所では読み取れない業務ルール、ハマった不具合の技術的な回避策等）
  だけをコメント対象にする。それ以外は書かない
- **機能追加の経緯・年月日・不具合対応の物語は書かない**：いつ・なぜ追加したかの
  経緯は`学習ノート.md`へ、現在の仕様は`docs/`配下の設計書へ書く。コードコメントには
  「今なぜこうなっているか」の技術的理由だけを残す（「経緯：学習ノート.md8.2」の
  ように参照だけ添えるのは可）

## その他

- **`any`を使わない**：型エラーは、Propsの渡し漏れやimportパスの不整合を疑って直す。
  `any`で握りつぶさない（`規約.md`②）
- **破壊的な操作の前に確認ダイアログを挟む**：タスク削除・退会など元に戻せない操作は、
  `window.confirm`等で誤操作防止を入れる（`TaskCard.tsx`の削除ボタンが例）
- **アイコンのみのボタンには`aria-label`を付ける**：テキストラベルがないボタン
  （閉じるボタン等）は`aria-label`でスクリーンリーダー対応する（`ImageLightbox.tsx`が例）
- **操作ボタンは権限を持つ人にしか出さない**：RLSで許可されている人（作成者・確認者等）
  以外には、操作ボタンの代わりに現在の状態を示す文言だけを出す（`TaskCard.tsx`が例）
