## 1. これは何のアプリか

社内向けの、1人〜少人数チーム用タスク管理ダッシュボードです。Supabase（PostgreSQL + Auth）を
バックエンドに使っており、メールアドレス＋パスワードでサインアップした複数のユーザーが、
実際にログインして同じタスクを共有できます。

- 複数のプロジェクトを作成し、プロジェクトごとにタスク・メンバーを分けて管理できる
  （プロジェクト管理機能。6.11・7章参照）
- タスクをカンバン形式（未着手／進行中／査読・承認待ち／完了）で管理する
- ダッシュボードで進捗率・期限超過・メンバー負荷などを可視化する
- タスクには「確認者（レビュアー）」を設定でき、査読待ち→承認 or 差し戻し、という簡易ワークフローを持つ
- 配色テーマを12種類（ダーク6種／ライト6種、既定はGRAPHITE）の中から選べる
- 表示名・アバター画像・パスワードなど、自分のプロフィールを設定ページから変更できる（退会も可能）

現在の画面上のアプリ名は **WORK PLUS**（サイドバーロゴは `W+`）です。
公開URL：https://work-plus-eosin.vercel.app/

状態管理ライブラリ（Redux等）やルーティングライブラリ（React Router等）は使っていません。

### 2.1 なぜSupabase（PostgreSQL）を選んだか

MySQL系サービスと比較検討した結果、Supabase（PostgreSQL）を採用しています。決め手は次の3点です。

- **無料枠の実用性**：2026年時点で「無料で使えるMySQLホスティング」はほぼ存在しない一方、
  Supabaseは無料枠（DB 500MB、Auth月間5万ユーザーまで）があり、ポートフォリオ用途に現実的
  （1週間アクセスが無いと自動的に一時停止するが、面接前にアクセスすれば復帰する程度の制約）
- **RLS（行レベルセキュリティ）**：「このユーザーは、このテーブルのこの行だけ見て良い／編集
  して良い」というルールをデータベース自体に直接書き込める機能。「担当者だけがタスクを見られる」
  「プロジェクトメンバーだけが操作できる」といった、このアプリで必要な制御と相性が良い。
  MySQLには標準で相当する機能が無く、同じことをやろうとするとアプリ側で毎回チェックを書く
  必要があり、実装量・バグの入り込む余地が増える
- **Auth・Storageが標準搭載**：認証（パスワードのハッシュ化・セッション管理・パスワード
  リセットメール送信など）やファイルストレージを自作せずに済む

フロントエンド採用向けのポートフォリオという目的を考えると、認証やインフラの自作に時間を
使うよりも、フロントエンドの作り込み（UI/UX・状態管理・型安全性など）に時間を使う方が
費用対効果が高いという判断です。

### 2.2 全体アーキテクチャ

独自のサーバー（Node.js/Expressなど）は挟まず、**フロントエンドから直接Supabaseを呼び出す**
構成（BaaS＝Backend as a Serviceパターン）です。アクセス制御はサーバーコードではなくRLS
ポリシー（DB側の設定）で行います。

```
React (App.tsx) ──── Supabaseクライアント(@supabase/supabase-js)
                          │
                          ├─ Auth（ログイン・ユーザー登録・セッション管理）
                          ├─ Database（PostgreSQL、RLSでアクセス制御）
                          └─ Storage（アバター画像）
```

## 4. 状態管理の考え方（重要）

このアプリの一番の設計方針は **「状態の所有権は1箇所（Appコンポーネントのインスタンス）に
一元化する」** という点です（`規約.md` ではこれを「Single Source of Truth（単一の真実の源泉）」
と呼んでいます）。

2026-09-03に、`App.tsx`が1713行まで肥大化した（いわゆる「Godコンポーネント」状態）ことを
受けて、状態・副作用・ハンドラーをドメインごとに`src/hooks/`配下の9個のカスタムフックへ
切り出すリファクタを行いました。**ただし、これはSSOTの原則を崩すものではありません**。
`useState`自体は`App()`コンポーネントインスタンスが呼び出すフック関数の中で呼ばれ続けており、
「状態の所有権が1箇所に集約されている」という規約①の趣旨は保たれたまま、「コードの物理的な
置き場所」だけをドメイン単位で整理した形になります。子コンポーネントが状態を直接書き換えない
という規約は変わらず、`App.tsx`はフックの戻り値を組み立てて子コンポーネントへPropsとして
渡す「合成層（コンポジションルート）」としての役割を持ちます。

```
App.tsx （フックを呼び出し、戻り値を合成してJSXを組み立てる）
 │
 ├─ useAuthSession()        … session / authLoading（Supabaseの認証セッション）
 ├─ useUsers()               … users（Supabaseのprofilesテーブルから取得したユーザー一覧）
 ├─ useProjectMembers()      … projectMembers / projectTaskCounts（メンバー一覧・進捗集計）
 ├─ useTheme()                … theme（個人のUI設定。localStorage）
 ├─ useViewNavigation()      … currentView（今どの画面を表示中か）・サイドバー開閉
 ├─ useProjects()             … projects / currentProjectId（参加中プロジェクト一覧・選択中ID）
 ├─ useTasks()                … tasks / tasksLoading・notificationTasks（タスク一覧）
 ├─ useNotifications()       … isNotifOpen / notificationSettings・通知一覧の導出
 ├─ useTaskFilters()         … filterUser / filterCategory / filterPriority（絞り込み条件）
 └─ App.tsx自身が持つ状態    … isModalOpen / editingTask / rejectTargetIdなど、まだ
                                フック化していないモーダル系の状態
       │
       │  Props（データを下に渡す）
       ▼
  Sidebar / DashboardView / KanbanBoard / ScheduleView / SettingsView / TaskForm / …
       │
       │  コールバック関数（「こう変更して」とApp.tsxに依頼する）
       ▲
  onUpdateStatus / onProcessAction / onAddTask など
```

子コンポーネント（例：`TaskCard`）は自分でタスクの中身を書き換えることはせず、必ず
`onProcessAction(id, 'approve')` のように **親から渡された関数を呼び出す** ことで
「変更してほしい」とリクエストします。実際に `tasks` を書き換えるのは`useTasks.ts`
（App.tsxから呼び出されるフック）内のハンドラーだけです。

複数のフックの状態を組み合わせないと計算できない派生値・ハンドラー（例：
`projectsNeedingOwnershipHandover`は`useProjects()`の`projects`と`useProjectMembers()`の
`projectMembers`の両方が必要）は、どちらのフックにも寄せず`App.tsx`側に残しています。これも
「状態の所有権の一元化」というSSOTの精神と矛盾しない設計判断です。

`currentView`（`'dashboard' | 'tasks' | 'schedule' | 'settings' | 'project' | 'notifications'`）
という文字列1つで表示する画面を切り替えています。React Routerのような外部ルーティング
ライブラリは使わず、条件分岐だけで画面遷移を実現しています（規約.mdで「一面集約型SPA」と
呼ばれている設計です）。

ダッシュボード／タスクボード／スケジュールの3画面は、選択中プロジェクト（`currentProjectId`）の
タスクだけをSupabaseから取得して表示します（`.eq('project_id', ...)`で絞り込み。6.11参照）。
未選択の間はこの3画面に「プロジェクトを選択してください」という案内が表示されます。

### 4.0 `src/hooks/`一覧

| フック | 役割 |
|---|---|
| `useAuthSession.ts` | session・認証状態・ログアウト・パスワード変更・退会 |
| `useUsers.ts` | 担当者一覧・自分のプロフィール更新 |
| `useTheme.ts` | 配色テーマ |
| `useViewNavigation.ts` | 画面切り替え・サイドバー開閉・アバター拡大表示 |
| `useProjects.ts` | プロジェクト一覧・選択・CRUD |
| `useProjectMembers.ts` | プロジェクトメンバー管理・メンバー数/タスク進捗の集計 |
| `useTasks.ts` | タスクCRUD・通知用タスク取得・20秒ポーリング |
| `useNotifications.ts` | 通知ベルの開閉・種類ごとのON/OFF設定・「自分宛て」アラート一覧の導出 |
| `useTaskFilters.ts` | グローバル操作フィルターバー（担当者/カテゴリ/優先度）と抽出件数・カテゴリ選択肢 |

フック同士が互いの戻り値を必要とし合う場合（例：`useProjects()`は`useProjectMembers()`の
`refreshProjectSummaries`を直接引数として要求する）は、TypeScriptのTDZ（Temporal Dead
Zone）の都合で呼び出し順序を守る必要があります。詳しい経緯・設計判断は`学習ノート.md`8.8を
参照してください。

### 4.1 データの永続化

`users` / `tasks` / ログイン状態（`session`）は、すべてSupabase（PostgreSQL + Auth + Storage）に
保存されます。一方、`theme`（配色テーマ）と`notificationSettings`（通知ベルのON/OFF設定）の
2つだけは「この端末・このブラウザでの見た目の好み」という個人のUI設定と位置づけ、あえて
Supabase化せず引き続きブラウザの`localStorage`に保存しています。

## 5. データモデル（型定義）

`src/types/task.ts` に定義されています。実際のDBスキーマ（列名・制約）は
`詳細設計書_認証DB編.md`2章を参照してください。

### Task（タスク1件）

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | `string` | タスクの一意なID |
| `title` | `string` | タスク名 |
| `description` | `string?` | 詳細説明（任意） |
| `status` | `TaskStatus` | 進行ステータス |
| `category` | `TaskCategory` | カテゴリ |
| `startDate` / `endDate` | `string` | 開始日／期日（`YYYY-MM-DD`） |
| `priority` | `TaskPriority` | 優先度 |
| `assignees` | `string[]` | 担当者のUser ID配列（複数選択可。ただし0人にはできない） |
| `reviewerId` | `string?` | 確認者（レビュアー）のUser ID |
| `returnReason` | `string?` | 差し戻し理由（差し戻されたときだけ入る） |
| `createdBy` | `string` | 作成者のUser ID（削除権限の判定に使用。RLSと揃える） |
| `subtasks` | `Subtask[]?` | サブタスク（チェックリスト）の配列 |
| `projectId` | `string` | 所属プロジェクトのID（NOT NULL）。6.11参照 |

### Subtask（サブタスク＝タスク内の簡易チェックリスト項目）

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | `string` | サブタスクの一意なID |
| `title` | `string` | サブタスクの内容 |
| `done` | `boolean` | 完了したかどうか |

サブタスクはあくまで親タスクの中の「進捗メモ・チェックリスト」という位置づけです。独自の
期日は持たず、常に親タスクの期日（`endDate`）を共有します。`status`や`returnReason`のような
承認フロー（査読・差し戻し）も持たせていません。「サブタスクごとに承認が要るのか？」という
曖昧さを生まないよう、あえてシンプルなチェックリストに留めている設計上の判断です。

### 各種の値の種類（Union型）

| 型名 | 取りうる値 | 画面上の表示 |
|---|---|---|
| `TaskStatus` | `todo` / `doing` / `review` / `done` | 未着手／進行中／査読・承認待ち／完了 |
| `TaskCategory` | `開発` / `デザイン` / `マーケ` / `その他` | そのまま表示 |
| `TaskPriority` | `low` / `medium` / `high` | 低／中／高 |
| `AppTheme` | 12種類（既定`graphite-dark`） | 設定ページのテーマタブに表示 |

### User（担当者・レビュアー）

Supabaseの`profiles`テーブル（`id` / `display_name` / `avatar_url`）から取得した実際のユーザー
一覧です。新規登録（サインアップ）すると、DB側のトリガー（`handle_new_user`）が自動的に
`profiles`へ1行追加します。

### Project（プロジェクト1件）

`id` / `name` / `description?` / `status`（`active` | `completed` | `archived`）/ `createdBy`。
メンバー一覧・タスク進捗は`Project`型自体には持たせず、`App.tsx`側で別のstate
（`projectMembers` / `projectTaskCounts`）として保持しています（6.11参照）。

## 6. 画面・機能一覧

### 6.1 ログイン画面（`pages/Login.tsx`）

Supabase Authの`signInWithPassword` / `signUp`を直接呼び出す認証画面です。

- 「サインイン」「新規登録」のタブで切り替え。新規登録時は表示名も入力する
- 新規登録後はメールアドレス確認が必須（Supabase Authのデフォルト設定）
- サインイン成功後の画面遷移は`App.tsx`側が`onAuthStateChange`を購読して行う
- よくあるSupabaseのエラーメッセージは`translateAuthError`関数で日本語に変換して表示する
- **ゲストログイン**：「ゲストとしてログイン」ボタンから、会員登録なしでSupabaseの匿名認証
  （`signInAnonymously`）を使ってその場でログインできる（詳細設計書_認証DB編.md1章参照）。
  ログアウトすると、作成したデモデータ・匿名アカウント自体は自動的に削除される

### 6.2 全体レイアウト（`App.tsx`）

- 左：サイドバー（開閉可能。スマホ幅ではオーバーレイ表示）
- 右上：共通ヘッダー（現在の画面名バッジ／選択中プロジェクト名バッジ／新規作成ボタン／通知ベル／設定ボタン／アバター）
- ヘッダー下：担当者・カテゴリ・優先度の絞り込みバー＋抽出件数（設定・プロジェクト管理・通知の3画面には表示されない）
- メイン：選択中の画面（ダッシュボード／タスクボード／スケジュール／プロジェクト管理／通知／設定）

配色テーマの切り替えは設定ページ（6.9参照）に集約されています。

#### 通知ベル

ヘッダー右側の🔔アイコンから、`notificationTasks`（選択中プロジェクトに絞らない、参加している
全プロジェクトのタスク）を毎レンダー時に導出する形で通知を表示します。「自分が担当者になって
いるタスク」を対象に、以下の4種類を通知します。

| 種類 | 条件 |
|---|---|
| 遅延中 | 自分が担当者・未完了・期日が今日より過去 |
| 当日締切 | 自分が担当者・未完了・期日が今日 |
| 差し戻された | 自分が担当者・ステータスが`doing`・`returnReason`あり |
| 承認待ち | 自分が確認者（`reviewerId`）・ステータスが`review` |

ドロップダウンは直近6件＋プロジェクト名タグのプレビューに徹し、「すべて見る（n件）→」から
通知専用画面（`NotificationsView.tsx`）へ遷移して全件を確認します。通知テーブル・既読/未読の
概念はなく、あくまで`tasks`の状態からその場で導出した「今この瞬間の通知一覧」です。他ユーザーの
操作を拾うため、ログイン時・20秒ごとのポーリング・自分のタスク操作の直後に取得し直しています。

### 6.3 サイドバー（`components/Sidebar.tsx`）

4つのメニュー項目（ダッシュボード・スケジュール・タスク一覧・プロジェクト管理）はすべて実際に
機能します。**プロジェクト管理**だけは他の項目と挙動が異なり、クリックするとその場で
アコーディオン開閉し、「＋新規プロジェクト」→参加中プロジェクトの一覧・選択→「すべて管理→」
の順で表示します（要件定義書_プロジェクト管理機能.md§2.1）。サイドバーが折りたたみ状態
（アイコンのみ）のときは、クリックで直接プロジェクト管理タブへ遷移する簡易挙動になります。

### 6.4 ダッシュボード画面（`components/dashboard/`）

`DashboardView.tsx` が入れ物となり、以下3つを縦に並べます。

1. **KpiCards**：完了率／タスク進捗／査読待ち／期限超過、の4枚のカード
2. **ProgressChart**：ステータス別の積層バー、メンバーごとの担当タスク数のバー
3. **GanttChart（締切・タイムライン）**：今日を中心に「2日前〜4日後」の7日分を表示。完了
   していない・期日のあるタスクのうち、期日が近い順に最大5件。期日超過は常に赤い「遅延」
   バッジが最優先で表示される（規約.mdの「遅延最優先ルール」）

いずれも、ヘッダーの絞り込みバーと連動して表示内容が変わります。

### 6.5 タスクボード画面（`components/kanban/`）

`KanbanBoard.tsx` が4カラム（未着手／進行中／査読・承認待ち／完了）を描画し、`TaskCard.tsx` が
各カードを描画します。

- カードはドラッグ＆ドロップでカラム間を移動。ただし**査読・承認待ち→進行中**の移動だけは
  直接せず「差し戻し理由モーダル」が開く
- カード下部のボタンはステータスに応じて変化する（進行中→承認申請、査読・承認待ち→確認者本人
  には差し戻し／承認完了、それ以外には「承認待ち」バッジのみ、常に削除）
- 期日超過（赤枠）・期日3日以内（黄枠・パルス点滅）・差し戻し中（薄い赤枠）の3種類の強調表示が
  あり、**遅延が常に最優先**
- カラムはコンテナクエリ（`@min-[1040px]:`）で実際の残り横幅を判定し、4カラムの等分グリッド
  ⇔横スクロール式の固定幅カラム表示を切り替える（6.10参照）

### 6.6 スケジュール画面（`components/schedule/ScheduleView.tsx`）

月間カレンダー形式で、タスクの期日（`endDate`）を日付ごとに表示します。日本の祝日を外部API
（[holidays-jp](https://holidays-jp.github.io/)）から取得してハイライトします（秘密キー不要の
公開API。取得失敗時もカレンダー自体は表示され、注記のみ出る）。実際に使える横幅が狭いときは
7列グリッドから縦1列の「リスト表示」に切り替わります（コンテナクエリ`@min-[640px]:`。6.10参照）。

### 6.7 タスク作成・編集モーダル（`components/TaskForm.tsx`）

- タスク名／詳細説明／サブタスク／作業担当者／確認者（レビュアー）／カテゴリ／優先度／期日、を入力
- サブタスクはタイトルを入力して追加でき、チェックボックスで完了・未完了を切り替え、個別に
  削除できる。カンバンのカードには「完了数/総数」の進捗バッジが表示される
- **作業担当者・確認者は、検索付きコンボボックス（`UserPicker.tsx`）で選択する**（2026-09-02
  再設計。入力すると名前で候補を絞り込め、選択済みはアバター付きのタグ表示〈×で解除〉になる）
- 作業担当者は複数選択（最低1人は必ず選択されている必要があり、`TaskForm.tsx`側の
  `handleAssigneeChange`が担保。`UserPicker.tsx`自体はこの業務ルールを持たない汎用部品）
- 確認者は単一選択で、**作業担当者に選ばれていないユーザー**の中から選ぶ（自分で自分の作業を
  承認できてしまう状態を防ぐため）
- 作業担当者・確認者の選択候補は、常に**選択中プロジェクトのメンバーのみ**に絞り込まれる
- **編集時のみ「プロジェクト」欄が表示される**。自分が参加している他のプロジェクトへタスクを
  移動でき、移動先のメンバーでなくなる担当者・確認者だけが自動的に選択から外れる
- 保存時、担当者・サブタスクは既存行をいったん全削除してから作り直す方式（詳細設計書_認証DB編.md2.3参照）
- **既知の制約**：確認者の候補は「選択中プロジェクトのメンバーのうち、担当者に選ばれていない
  ユーザー」から絞り込むため、メンバーが少ないうち（特に自分1人だけの場合）は候補が0人になる
  （`UserPicker.tsx`のドロップダウンには案内文が出る。TODO.md参照）

### 6.8 差し戻し理由モーダル（`components/RejectReasonModal.tsx`）

差し戻し理由を自由入力できるテキストエリア。`required`属性に加え、送信時に`trim()`後の空文字を
弾くことで、通常入力・空白のみ入力のどちらでも「差し戻し理由は必ず書く」挙動を保証しています。

### 6.9 設定ページ（`components/settings/`）

`SettingsView.tsx`が入れ物となり、タブ切り替えで以下5つのセクションを出し分けます。

1. **プロフィール**（`ProfileSection.tsx`）：表示名編集・アバター画像アップロード・パスワード変更
2. **テーマ**：12種類の配色テーマから選択
3. **通知**：通知ベルの4種類を個別にON/OFF
4. **データ**：サンプルデータへのリセット、**オーナー引き継ぎ**（`OwnershipHandoverSection.tsx`。
   自分がオーナーで他にもメンバーがいるプロジェクトが残っている間は退会ボタンの代わりに表示）、
   退会（`DangerZoneSection.tsx`。`delete_own_account`経由）
5. **アプリについて**（`AboutSection.tsx`）：アプリ名・バージョン・紹介文・技術スタック・主な
   機能・リンクをまとめた紹介カード

### 6.10 モバイル（スマホ）・タブレット対応

- サイドバーはスマホ幅ではオーバーレイ表示、項目選択と同時に自動で閉じる
- フィルターバー・設定ページのタブは横スクロールではなく`flex-wrap`で折り返す
- **タスクボード・スケジュール・プロジェクト管理タブは、ビューポート幅ではなくコンテナクエリ
  （`@container` / `@min-[…]:`）でレイアウトを切り替える**。理由：これらの画面は「横に何列も
  並べる」レイアウトのため、実際に使える横幅（サイドバー開閉で変わる）が直接崩れやすさに
  関わる。ビューポート幅だけを見るブレークポイントでは、ビューポート自体は`md`以上でも
  サイドバーを開いた分だけ実際の残り幅が足りない、というケースを判定できない

### 6.11 プロジェクト管理機能（`components/project/` 他）

複数のプロジェクトを作成し、プロジェクトごとにタスク・メンバーを分けて管理できるようにする
機能です（要件は`要件定義書_プロジェクト管理機能.md`、DB設計は`詳細設計書_認証DB編.md`参照）。

- **選択・切り替え**：サイドバーのアコーディオンから素早く切り替え。選択中プロジェクトIDは

- **「プロジェクト管理」タブ**（`ProjectManagementView.tsx`）：参加プロジェクトをカード形式で
  一覧表示（ロール・メンバー数・タスク進捗％）。検索＋ステータスタブで絞り込み
- **メンバー管理・オーナー譲渡**（`MemberManagementModal.tsx`）：オーナーはメンバーの追加・
  削除・オーナー譲渡ができる
- **タスクのプロジェクト間移動**：6.7参照
- **退会時のオーナー引き継ぎ**：6.9参照
- **通知の全プロジェクト横断対応**：6.2参照

## 8. 主要な設計判断のまとめ

- **RLSポリシーは「プロジェクトメンバーのみアクセス可」を基本方針とする**（プロジェクト管理
  機能導入前は「ログインしていれば全員が全タスクを見られる」方式だったが、11章導入時に
  プロジェクト単位の隔離へ移行）
- **新規登録はオープン方式**（誰でも登録可能。招待制にはしない）
- **メールアドレス確認は必須**（Supabase Authのデフォルト設定をそのまま使用）
- **楽観的更新はせず、書き込み後は毎回サーバーから再取得する**（`refreshTasks()`等）。
  レスポンスの体感速度よりも正しさ・堅牢性を優先する判断
- **状態管理ライブラリ・外部ルーターは使わない**（`useState`中心のSSOT、`currentView`文字列
  切り替えのみ）
- **状態はカスタムフックへドメインごとに分割するが、Context APIは導入しない**（2026-09-03、
  `App.tsx`のフック分割リファクタ）。状態の所有権は`App()`コンポーネントインスタンス1つに
  一元化されたままであり、規約①のSSOTと矛盾しないという整理のもとで実施した（4章参照）
- **役職（ロール）ベースの厳格な権限制御は、プロジェクト単位のオーナー／メンバーの2値に
  留める**。組織全体の管理者ロールはYAGNI判断で見送り（拡張は後乗せ可能な設計にしてある）

## 9. 既知の制約・設計上の境界

「今後直す予定」ではなく、意図的にそうなっている恒久的な仕様・制約です（未着手のバックログは
`TODO.md`を参照）。

- **配色テーマ・通知ON/OFF設定だけはlocalStorage保存**：個人のUI設定であり複数端末間で
  共有する必要が無いため、あえてSupabase化していません
- **祝日API（外部API連携）への依存**：スケジュール画面は`holidays-jp`の祝日APIに依存して
  います。秘密キー不要の公開APIのため直接ブラウザから呼び出していますが、取得に失敗しても
  カレンダー自体の表示は止まらないようフォールバック済みです。今後、秘密のAPIキーが必要な
  外部APIを使う機能を追加する場合は、Supabase Edge Functionsなど秘密鍵をサーバー側に隠す
  仕組みを別途整えてから実装する方針です
- **サブタスクは承認フローを持たない簡易チェックリスト**：親タスクの承認・差し戻しフローとは
  独立しており、サブタスク単体の承認や個別期日はありません
- **ゲスト（匿名）アカウントのログアウト時、ブラウザの開発者ツールに403エラーのネットワーク
  ログが表示されることがある**：`delete_own_account()`で自分自身の`auth.users`行を削除した
  直後に`signOut()`を呼ぶと、Supabase Auth側が「JWTのsubクレームに対応するユーザーが
  見つからない」と判断し、ログアウトのAPIリクエスト自体が失敗する（既知のSupabase Auth側の
  挙動）。アプリの動作としては実害がなく、ブラウザが自動的に表示するネットワークエラーログ
  のため、アプリのコード側で完全に消すことはできません（詳細設計書_認証DB編.md1章参照）
- **タスク・ユーザーデータはSupabaseに保存されるため、別のブラウザやスマホからでも同じ
  アカウントでログインすれば同じデータが見えます**。配色テーマ・通知ON/OFF設定はlocalStorage
  保存のため、この2つだけは端末・ブラウザごとに独立したままです
