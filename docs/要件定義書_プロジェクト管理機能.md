## 0. 現状とスコープ

- サイドバーの4項目（ダッシュボード／スケジュール／プロジェクト管理／タスク一覧）のうち、
  「プロジェクト管理」だけがクリックすると「近日公開」というプレースホルダーが出るのみで、
  中身は未実装だった
- 従来のタスクは「1つの共有掲示板」モデル。ログインしている全員が同じ`tasks`テーブルを
  共有し、担当者・カテゴリ・優先度で絞り込んで見ているだけで、「プロジェクトごとに分ける」
  という概念自体が存在しなかった
- **本機能のスコープ（確定）**：本格的な複数プロジェクト管理を導入する。「プロジェクト」を
  新しいデータの単位として設け、タスクは必ずどれか1つのプロジェクトに属するようにする。
  ダッシュボード・カンバン・スケジュールの3画面も、プロジェクトごとに切り替えて見られるように
  する（詳細は2章）

## 1. 全体イメージ

```
【変更前】
ログイン中のユーザー全員 ── 1つの共有tasksテーブル（プロジェクトの区別なし）

【変更後】
ログイン中のユーザー
  └─ 自分が所属するプロジェクト一覧（projects × project_members）
        └─ プロジェクトA を選択中 ── ダッシュボード／タスクボード／スケジュールは
                                        すべて「プロジェクトAのタスクだけ」を表示
        └─ プロジェクトB を選択中 ── 同様にプロジェクトBのタスクだけを表示
```

ポイントは、**ダッシュボード・タスクボード・スケジュールの3画面を作り直すのではなく、
「今どのプロジェクトを見ているか」という状態を1つ追加し、既存の3画面をそのプロジェクトで
絞り込んで表示するだけにする**こと。`filterUser` / `filterCategory` / `filterPriority`と
同じように、`currentProjectId`という状態をApp.tsxに1つ追加し、Supabaseへの問い合わせに
`.eq('project_id', currentProjectId)`を足すだけで済むようにする。これにより、
既存のKanbanBoard.tsx / DashboardView.tsx / ScheduleView.tsxはほぼ改修不要。

## 2. UI/UX要件

「プロジェクト管理のUI/UXはどうなるか」について、確定した方針をまとめる。大きく分けて
**(A) サイドバーからのプロジェクト切り替え**と、**(B) プロジェクト管理タブでの一覧・作成・
メンバー管理**の2つの動線がある。

### 2.1 (A) サイドバーのアコーディオン式プロジェクト切り替え（確定）

ヘッダーに別途スイッチャーを新設する案もあったが、**サイドバーの「プロジェクト管理」項目
自体をアコーディオンにする**方針で確定した。既存のメニュー項目（ダッシュボード／
スケジュール／プロジェクト管理／タスク一覧）はそのままに、「プロジェクト管理」だけクリックで
開閉するようにする。

```
サイドバー（閉じた状態）              サイドバー（「プロジェクト管理」を開いた状態）
┌────────────────────┐        ┌────────────────────┐
│ 🏠 ダッシュボード         │        │ 🏠 ダッシュボード         │
│ 📅 スケジュール           │        │ 📅 スケジュール           │
│ 📁 プロジェクト管理  ▾    │        │ 📁 プロジェクト管理  ▴    │
│ ✅ タスク一覧             │        │   ● プロジェクトA  ← 選択中│
│                        │        │     プロジェクトB         │
│                        │        │     プロジェクトC         │
│                        │        │     ＋ 新規プロジェクト     │
│                        │        │     すべて管理 →           │
│                        │        │ ✅ タスク一覧             │
└────────────────────┘        └────────────────────┘
```

- 「プロジェクト管理」をクリックするとアコーディオンが開閉し、自分が参加しているプロジェクトが
  一覧表示される（他のメニュー項目のように別画面へ即座に遷移するのではなく、その場で展開する）
- プロジェクト名をクリックすると、それが「現在のプロジェクト（`currentProjectId`）」になり、
  自動的にダッシュボードへ遷移する。以降、ダッシュボード／タスクボード／スケジュールの3タブは
  すべてこのプロジェクトの内容を表示する
- 選択中のプロジェクトには●印などで現在地を示す
- 一覧の下に「＋新規プロジェクト」（2.2のモーダルを開く）と「すべて管理→」
  （2.3の一覧・メンバー管理ページへ遷移する）を常設する
- 選択状態は`theme`と同じ扱いで`localStorage`に保存し、リロードしても直前に見ていた
  プロジェクトを復元する
- サイドバーが折りたたみ状態（アイコンのみ表示）のときは、アコーディオンではなく
  クリックで2.3のプロジェクト管理ページへ直接遷移する簡易的な挙動にする（折りたたみ幅では
  展開表示するスペースが無いため）
- ダッシュボード／タスクボード／スケジュールの3タブは、現在のプロジェクトが未選択の状態
  （初回ログイン時など）では「プロジェクトを選択してください」という案内を出し、内容は
  表示しない

### 2.2 プロジェクト作成・編集モーダル

- 入力項目：プロジェクト名（必須）／説明（任意）／ステータス
- **ステータスは「進行中」「完了」「アーカイブ」の3値で確定**（「完了」は作業自体は終わったが
  プロジェクトとしては残しておきたい状態、「アーカイブ」は一覧から隠したい過去のプロジェクトを
  示す状態、という役割分担。サイドバーのアコーディオンや一覧では**アーカイブのみ**デフォルト
  非表示にし、一覧側に「アーカイブ済みを表示」の切り替えを設ける）
- 作成すると、作成者が自動的に`project_members`へ「オーナー」として登録される
  （タスクの`createdBy`と同じ考え方）
- 編集はオーナーのみ可能（7章）

### 2.3 (B) プロジェクト管理タブ（プロジェクト一覧・メンバー管理ページ）

サイドバーのアコーディオンが「素早い切り替え」用の動線だとすると、こちらは「一覧性・管理操作」
のための画面。サイドバーの「プロジェクト管理」から見ると、アコーディオンの「すべて管理→」
経由でも到達できる。

```
┌───────────────────────────────────────────┐
│ プロジェクト管理                    ［＋ 新規プロジェクト］ │
├───────────────────────────────────────────┤
│ ┌─────────────┐ ┌─────────────┐ ┌───────────┐ │
│ │ プロジェクトA      │ │ プロジェクトB      │ │ プロジェクトC    │ │
│ │ オーナー：あなた    │ │ メンバー           │ │ オーナー：あなた  │ │
│ │ 👤👤👤 +2人       │ │ 👤👤 2人           │ │ 👤 1人          │ │
│ │ 進捗 ████░░ 62%   │ │ 進捗 █░░░░░ 12%   │ │ 進捗 ██████ 100%│ │
│ │        ［開く］    │ │        ［開く］    │ │      ［開く］    │ │
│ └─────────────┘ └─────────────┘ └───────────┘ │
└───────────────────────────────────────────┘
```

- 自分が参加している（`project_members`に自分の行がある）プロジェクトをカード形式で並べる
- 各カードに表示する情報：プロジェクト名／自分のロール（オーナー・メンバー）／メンバー数
  （アバターを重ねて数人分表示、他は「+n」）／タスク件数・完了率の簡易サマリー／
  「開く」ボタン（クリックで2.1の「現在のプロジェクト」を切り替え、ダッシュボードへ遷移）
- カード右上（オーナーのみ）に「編集」「メンバー管理」「削除」のメニューを表示
- 参加プロジェクトが0件のとき（新規ユーザー等）は空状態の案内＋作成ボタンを大きく表示

### 2.4 メンバー管理

- プロジェクトカードの「メンバー管理」から、既存の登録ユーザー（`profiles`）の中から選んで
  メンバーを追加できる（担当者選択と同じUI・体験を流用）
- オーナーはメンバーの削除、他メンバーへの「オーナー譲渡」ができる
- メンバー自身が「このプロジェクトから抜ける」こともできる。オーナー本人は、他の誰かに
  オーナーを譲渡するまで抜けられない（7.4・6.3参照）

### 2.5 タスクのプロジェクト間移動（確定：対応する）

`TaskForm.tsx`の編集画面に「プロジェクト」欄を追加し、自分が参加している他のプロジェクトへ
タスクを移動できるようにする。担当者・確認者と同様、移動先プロジェクトのメンバーで
なくなる担当者・確認者がいる場合は、該当者だけを自動的にクリアする。

## 3. データモデル設計（要件定義時点の案）

### 3.1 `projects`（プロジェクト本体）

```sql
create table projects (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  description text,
  status text not null default 'active' check (status in ('active', 'completed', 'archived')),
  created_by uuid references profiles(id) not null,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

### 3.2 `project_members`（プロジェクトとメンバーの中間テーブル）

```sql
create table project_members (
  project_id uuid references projects(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  role text not null default 'member' check (role in ('owner', 'member')),
  joined_at timestamptz default now(),
  primary key (project_id, user_id)
);
```

`task_assignees`（詳細設計書_認証DB編.md）と同じ「中間テーブルで多対多を表す」パターン。

### 3.3 `tasks`への追加

```sql
alter table tasks add column project_id uuid references projects(id);
-- 移行完了後、not nullに変更する（3.4参照）
```

### 3.4 既存タスクの移行方針

現在Supabase上にある既存タスクは、まだプロジェクトに属していない。マイグレーション実行時に
以下を自動で行う。

1. 「（移行前タスク）」のような名前で、現在の全ユーザーをメンバーとする既定プロジェクトを
   1つ自動作成する
2. 既存の全タスクの`project_id`をそのプロジェクトのIDで一括更新する
3. その後`tasks.project_id`に`not null`制約を付け、以降のタスク作成では必ずプロジェクトが
   必須になるようにする

移行後にプロジェクト名の変更や、タスクの別プロジェクトへの移動（2.5）ができるため、
ユーザー側で後から整理し直せる。

## 4. ダッシュボード・タスクボード・スケジュールへの影響

- 3画面とも、Supabaseへの問い合わせに`project_id = currentProjectId`の絞り込みを追加するだけ
- フィルターバー（担当者・カテゴリ・優先度）は現状通り「選択中プロジェクト内での」絞り込みとして
  そのまま使える
- **通知ベルの範囲は「自分が参加している全プロジェクトを横断して通知する」で確定**。
  選択中プロジェクトだけに絞ると、自分が今見ていない別プロジェクトの承認待ちなどに気づけず
  本末転倒になるため。通知アイテムをクリックした際、そのタスクが選択中でない別プロジェクトの
  ものであれば、`currentProjectId`をそのプロジェクトへ自動的に切り替えてから編集モーダルを
  開く挙動にする
- サイドバーの「タスク一覧」タブは、これまで通り現在のプロジェクトのカンバンボードを表示する
  役割になる（呼び名が紛らわしくなるため、「プロジェクト管理」＝一覧・切り替え・メンバー管理、
  「タスク一覧」＝選択中プロジェクトのカンバン、という役割分担を明確にする）

## 5. サンプルデータ・退会機能への影響

- **設定ページの「サンプルデータへのリセット」は「いったんこれまで通り」で確定**。
  プロジェクト単位への変更は見送り、現状通り「全プロジェクト横断で、自分が作成したタスクを
  削除して初期サンプルへ戻す」挙動のままにする（プロジェクトを跨いだサンプルタスクが
  作られる形になるが、そもそも開発中の動作確認用の機能のため実害は小さいと判断）
- 退会（アカウント削除）機能への影響は、6章で詳しく扱う（オーナー権限の引き継ぎが必要）

## 6. 退会（アカウント削除）とオーナー権限の引き継ぎ（確定）

「退会するときにオーナー権限を指定した人に渡せるのが一番よい」という方針で確定した。
既存の`delete_own_account`関数をそのまま拡張するのではなく、**オーナー譲渡を独立した機能として
先に用意し、退会フローの中でそれを利用する**設計にする（2.4で触れた「オーナーがメンバーへ
オーナー権限を譲渡する」通常の機能と、退会時の処理を同じ仕組みで実現できるため、二重に
作らずに済む）。

### 6.1 オーナー譲渡用の関数（新規）

実装内容は`詳細設計書_認証DB編.md`2.9を参照。

### 6.2 退会フロー（フロントエンド側の流れ）

1. 退会ボタンを押すと、まず「自分がオーナーで、かつ他にメンバーがいるプロジェクト」を
   （フロント側で`project_members`を参照して）調べる
2. 該当プロジェクトが1件以上あれば、退会確認ダイアログの前に「引き継ぎが必要なプロジェクトが
   あります」という画面を挟み、プロジェクトごとに新しいオーナーを選択してもらう
   （担当者・確認者選択と同じUIを流用）
3. 選択された組み合わせぶんだけ`transfer_project_ownership`を呼び出し、すべて成功したら
   通常の退会確認（パスワード再入力＋`window.confirm`）に進み、`delete_own_account`を呼ぶ
4. **自分がオーナーで、かつ他にメンバーがいないプロジェクト**（自分1人だけのプロジェクト）は
   引き継ぎ先が存在しないため、退会と同時にそのプロジェクトごと削除する（自分が単独作成した
   タスクが退会時に削除されるのと同じ考え方）

## 7. 権限（ロール）設計

### 7.1 RLS方針

- **`projects`**：閲覧はメンバーのみ／作成はログイン済みなら誰でも／更新・削除はオーナーのみ
- **`project_members`**：閲覧はメンバーのみ／追加・削除・ロール変更はオーナーのみ
  （自分自身の脱退のみ本人にも許可）
- **`tasks`**：既存ポリシー（閲覧・作成・更新はログイン済みなら誰でも、削除は作成者のみ）に
  「かつ、そのタスクのプロジェクトのメンバーであること」という条件を追加する

### 7.2 今回実装する権限まとめ

| 操作 | オーナー | メンバー | 非メンバー |
|---|---|---|---|
| プロジェクトの閲覧 | ○ | ○ | × |
| プロジェクト内タスクの閲覧・作成・更新 | ○ | ○ | × |
| プロジェクト内タスクの削除 | ○（自分の作成分） | ○（自分の作成分） | × |
| プロジェクト名・説明・ステータスの編集 | ○ | × | × |
| メンバーの追加・削除 | ○ | × | × |
| プロジェクトの削除 | ○ | × | × |
| オーナー譲渡（6.1） | ○ | × | × |

### 7.3 組織全体の管理者ロールについて（TODO・見送り）

組織全体の管理者ロールは、実は`profiles`に`app_role`列を1つ足し、既存のRLSポリシーへ
「または管理者なら許可」というOR条件を追加するだけで後乗せできる、スキーマを作り直す必要の
ない拡張である。

```sql
-- 将来追加する場合のイメージ（未実装）
alter table profiles add column app_role text not null default 'member' check (app_role in ('admin', 'member'));
```

このアプリには現状「組織」という概念自体が無く、管理者が実際に何を管理するのかがまだ
定義できていないため、YAGNI判断で見送った。

### 7.4 オーナーが1人しかいない場合の扱い

- 通常時：オーナーは、他のメンバーにオーナーを譲渡（6.1）するまでプロジェクトから
  自主的に脱退できない
- 退会時：自分1人だけのプロジェクトはプロジェクトごと削除、他にメンバーがいる場合は
  退会前に譲渡が必須（6章）
