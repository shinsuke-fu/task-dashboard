# WORK PLUS タスク管理機能 要件定義書

この文書は、プロジェクト管理機能を除く「タスク管理ダッシュボード」本体（認証・カンバン・
ダッシュボード・スケジュール・通知・設定）の要件定義書です。当初これらの機能は要件定義書を
作らず実装を先行させたため、2026-09-02に実装済みの内容から遡って書き起こしました。今後
この領域に変更を加える際は、実装のたびにこの文書も更新することを想定しています。

プロジェクト管理機能の要件は`要件定義書_プロジェクト管理機能.md`、実装済みの詳しい仕様は
`基本設計書.md`・`詳細設計書_認証DB編.md`を参照してください。

作成日：2026-09-02（実装済みの内容から書き起こし）

---

## 0. 対象・想定ユーザー

- 社内向けの、1人〜少人数チームで使うタスク管理ダッシュボード
- 想定ユーザーはログイン済みの登録ユーザー。**「担当者」「確認者（レビュアー）」の区別は
  タスク単位で付くロールであり、ユーザーアカウント自体に固定の権限段階（管理者／一般等）は
  設けない**（プロジェクト単位のオーナー／メンバーの区別のみ。`要件定義書_プロジェクト管理機能.md`参照）
- ポートフォリオ公開を前提とし、会員登録せずその場で試せる「ゲスト（匿名）ログイン」も
  提供する

---

## 1. 全体イメージ

```
ログイン（メール＋パスワード or ゲスト）
  └─ プロジェクトを選択
        ├─ ダッシュボード：進捗・遅延状況を俯瞰する
        ├─ タスクボード（カンバン）：タスクを作成・更新・承認する
        ├─ スケジュール：期日をカレンダーで俯瞰する
        └─ 通知：自分に関係する変化に気づく
  └─ 設定：プロフィール・テーマ・通知ON/OFF・退会
```

タスクは常にどれか1つのプロジェクトに属する。担当者・確認者は登録ユーザーの中から選ぶが、
選択候補は選択中プロジェクトのメンバーに絞り込まれる。

---

## 2. 認証・アカウント要件

| 要件 | 内容 |
|---|---|
| サインアップ／サインイン | メールアドレス＋パスワード方式。新規登録はオープン（招待制にしない） |
| メール確認 | 新規登録後、確認メール内リンクをクリックするまではログインできない |
| ゲストログイン | 会員登録・パスワード入力なしで、その場でアプリを試せる。ログアウト時に作成した
  データ・アカウント自体を自動的に片付ける（DBに残骸を溜めない） |
| パスワード再設定 | サインイン画面からメールでのパスワード再設定を行える |
| プロフィール編集 | 表示名・アバター画像を変更できる |
| パスワード変更 | ログイン中に現在のパスワードで本人確認のうえ変更できる |
| 退会（アカウント削除） | 自分のデータ（作成したタスク・アカウント）を削除できる。パスワード再認証と
  確認ダイアログを必須にする。プロジェクトのオーナーである場合は、先に他メンバーへの
  引き継ぎを要求する（`要件定義書_プロジェクト管理機能.md`6章） |

## 3. タスク管理要件

### 3.1 タスクの基本項目

タスク名（必須）・詳細説明（任意）・カテゴリ（開発／デザイン／マーケ／その他）・優先度
（低／中／高）・開始日／期日・作業担当者（複数・最低1人必須）・確認者（単一・任意）・
サブタスク（チェックリスト、任意）。

### 3.2 ステータスと承認フロー

タスクは「未着手／進行中／査読・承認待ち／完了」の4状態を持ち、次のワークフローに従う。

```
未着手 → 進行中 → （承認申請）→ 査読・承認待ち ─(承認)→ 完了
                                          └─(差し戻し・理由必須)→ 進行中
```

- 進行中から査読・承認待ちへは「承認申請」操作で進む
- 査読・承認待ちから完了へは、**確認者本人のみ**が「承認完了」操作を行える
- 査読・承認待ちから進行中への差し戻しは、**確認者本人のみ**が行え、差し戻し理由の入力を必須とする
- 確認者本人以外には、承認・差し戻しの操作ボタンの代わりに「承認待ち」という現在の状態表示のみを見せる

### 3.3 担当者・確認者の選定ルール

- 作業担当者は複数選択でき、最低1人は必ず選択されていなければならない
- 確認者は単一選択で、**作業担当者に選ばれていないユーザー**からのみ選べる（自分の作業を
  自分で承認できてしまう状態を防ぐため）
- 担当者・確認者の選択候補は、常に選択中プロジェクトのメンバーに絞り込まれる

### 3.4 遅延最優先ルール（最重要のUI要件）

期日を過ぎた未完了タスクは、他のどんな状態（査読待ち・差し戻し中など）よりも「遅延」の
見た目（強調表示）を最優先で表示しなければならない。これはこのアプリのUI上もっとも
重要な一貫性要件であり、他の状態表示に上書きされてはならない（`規約.md`③）。

### 3.5 サブタスク（チェックリスト）

タスクの中に、タイトルと完了フラグだけを持つ簡易チェックリストを持てる。独自の期日・承認
フローは持たず、親タスクの期日を共有する簡易な位置づけとする。

### 3.6 タスクの削除

タスクの削除は作成者本人のみが行える。

## 4. ダッシュボード要件

選択中プロジェクトについて、以下を可視化する。

- 完了率／タスク進捗（完了数・総数）／査読待ち件数／期限超過件数の要約
- ステータス別の件数分布
- メンバーごとの担当タスク数（負荷の可視化）
- 直近の締切をタイムライン形式で俯瞰できること（今日を基準に近い順）

いずれも、担当者・カテゴリ・優先度による絞り込みと連動して表示内容が変わること。

---

## 5. スケジュール要件

- タスクの期日を月間カレンダー形式で俯瞰できること
- 日本の祝日をハイライト表示すること（取得に失敗してもカレンダー自体の表示は継続すること）
- 画面幅が狭い場合でも一覧性を保てるレイアウトであること（横スクロールに頼らない）

---

## 6. 通知要件

- 自分が担当者になっているタスクについて、「遅延中」「当日締切」「差し戻された」を通知する
- 自分が確認者に指定されているタスクについて、「承認待ち」を通知する
- 通知は選択中プロジェクトに限らず、自分が参加している全プロジェクトを横断して検知できること
  （見ていないプロジェクトの承認待ち等に気づけなくなることを避けるため）
- 通知の種類ごとにON/OFFを設定できること
- 通知をクリックすると、該当タスクの編集画面に直接遷移できること

---

## 7. 設定・パーソナライズ要件

- 配色テーマを複数種類から選べること（個人の見た目の好みであり、他ユーザーと共有しない設定とする）
- 通知の種類ごとのON/OFFを設定できること（同上、個人設定）
- サンプルデータへのリセット機能を提供すること（自分が作成したタスクのみが対象。他ユーザーの
  データに影響しないこと）
- アプリの概要・技術スタック・主な機能を紹介するページを提供すること（社内共有等での紹介用途）

---

## 8. 非機能要件

- **レスポンシブ対応**：スマートフォン・タブレット幅でも一覧性を保ち、横スクロールに頼った
  レイアウトを避けること
- **状態管理の一元化**：画面をまたぐ状態は単一の場所（ルートコンポーネント）に集約し、
  子コンポーネントが直接書き換えないこと（`規約.md`①）
- **アクセス制御はデータベース側でも保証すること**：UI側でボタンを隠すだけでなく、権限の
  無い操作はデータベース側（RLS）でも拒否できること
- **誤操作防止**：削除・退会など元に戻せない操作の前には確認ダイアログを挟むこと
